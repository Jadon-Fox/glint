## 1. Closest prior art: SpAx, tiered per-token column fetch for offloaded weights ([arXiv:2610.02598](https://arxiv.org/abs/2610.02598), Oct 2026)
*Read depth:* abstract and main text through section 6.2 verbatim; appendices B-D and part of 6.3 only as a model summary.
- **Method:** per token and per matrix group, rank input channels by |x|. The top tier is read in the deployment format (BF16 or Q4_K_M), a middle tier is read as a 2-bit code (a trellis-coded or two-scale scalar approximation of the same column, stored as a second copy), and the rest is **not read at all**. All weights live in CPU RAM or on NVMe; embeddings, head and KV cache stay on the GPU. Offline calibration on WikiText-2 sets the tier sizes under a byte budget. Columns are stored contiguously in input order and adjacent selected ranges are merged into single reads. Built on llama.cpp, batch 1, RTX 4090 on PCIe 4.0 x8, 128 GB RAM.
- **Results (Llama-3.1-8B, WikiText-2 dense PPL 6.24):** at +10% perplexity, SpAx needs 27% of the bytes against 57% for TEAL; speedups over dense offloaded decoding 3.86x average (up to 5.57x) for BF16 and 2.06x (up to 2.74x) for Q4_K_M at +10% PPL. lm-eval at +10%: ARC-C 52.1 to 49.1, HellaSwag 60.8 to 58.5, MMLU 65.4 to 62.1, GSM8K (free-running) 50.2 to 43.9. The paper is internally inconsistent in places (its section 6.2 quotes different speedups from its abstract), which the reader flagged.
- **What differs from GLINT:** SpAx has **no resident base**: the bottom tier is dropped, not corrected, so quality loss is its operating point (+10% PPL, up to about 6 points on GSM8K). GLINT keeps a 4-bit hole for every weight on the GPU and fetches a correction, and our acceptance rule is far stricter than +10% PPL (free-running token agreement with the full model).
- **What GLINT can take from it:** the three-tier idea (full / cheap code / nothing), the contiguous-in-index-order layout with merged ranges (we reached the same layout from the fetch benchmark), and TEAL as the activation-sparsity baseline. SpAx also reports that its trellis reconstruction costs 52-64 ms of GPU time per token against 22-27 ms for the scalar variant, a reminder that the decode of a coded residual is not free (our 2-/3-bit plug emulation assumed free unpacking).

## 3. What the searches did **not** find
No paper that combines (a) a resident low-bit base for every weight, (b) a per-token, activation-selected higher-precision **residual** fetched from host RAM over PCIe, and (c) a free-running, token-exact fidelity gate. SpAx is closest (it fetches per token by |x| but drops the bottom tier); DecDEC is the original for the residual-in-CPU-RAM idea; MosaicQuant is the static on-GPU analogue; AnyBCQ/PagedWeight are the nested-precision analogues. This is a limited set of searches, not a literature review.

## 4. A point on the base: calibrated 4-bit methods set a lower floor than the NF4 hole
One 2026 preprint found by search ([QAM-W, arXiv:2605.26339](https://arxiv.org/abs/2605.26339), via a search summary, **not read**) lists QTIP at 4 bits with +1.32% perplexity and KL 0.010 against +2.15% / 0.029 for its own method. If that holds, calibrated and trellis-coded 4-bit bases sit at KL about 0.01, against 0.03-0.15 for GLINT's data-free NF4 hole on our four models and 0.021-0.048 for llama.cpp's Q4_K_M/Q4_0. This repository's own measurements agree in direction (`COMPETITOR_llamacpp_phi4mini.md`: fold only is worse than the 4-bit llama.cpp quantizers). The residual then has less to correct.

## 5. What this suggests for the plan (recommendations, not results)
1. **Keep free-running agreement as the acceptance gate and add probes.** Three independent sources (FlexQuant, ResCom, the perplexity paper) say short-form metrics hide generation-time damage; our 12-prompt study is consistent. Add induction and key-value retrieval probes to the acceptance suite.
2. **Test a tiered plug before more fraction sweeps.** SpAx's middle tier suggests: top-k channels at the 4-bit plug, the next band at a cheaper code, the rest base-only. Our emulation found a 3-bit code nearly free at full plug (KL 2.1e-3, 95.8% agreement) and a 2-bit code unusable at full plug (60.2%), so the cheap tier would be 3-bit; the emulation (`GLINT_PLUG_BITS`) already supports a per-band variant with a small change.
3. **Make the base the next variable, not the fetch.** A calibrated 4-bit base (GPTQ/AWQ-style rounding or a trellis code) could cut the fold-only floor several-fold at the same 4.5 bits; the INT4 base measured here (PR #98) is uniform and uncalibrated, and the NF4 hole is data-free. This also bears on the operator's open question about INT4-stored versus the NF4 hole. GPTQ/AWQ/HQQ tooling needs Python environments that workspace policy U-011 blocks; llama.cpp's own imatrix quantization is an available calibrated proxy.
4. **Do not claim a speed lead over SpAx or DynamicInfer.** The setups differ (SpAx: all weights offloaded, +10% PPL tolerance, RTX 4090 on PCIe 4.0 x8; ours: 4-bit base resident, token-exact tracking, RTX 3060 on PCIe 3.0 x16). A like-for-like test would run SpAx's rule (top tier / 2-bit mid tier / skipped) in this harness at matched bytes.
5. **Count decode cost of any coded residual** (SpAx's trellis: 52-64 ms GPU time per token) before assuming packed 3-bit fetch is a win.
